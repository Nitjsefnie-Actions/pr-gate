# Pull request admission gate

A SHA-pinnable GitHub composite action that checks pull-request descriptions
against the consumer repository's template and assigned issues. It can comment,
close, and automatically reopen a corrected PR that it closed itself.

## Usage

Pin the action to a reviewed full commit SHA from this repository. The
`# vX.Y.Z` comment after the pin names the reviewed release carrying that
SHA; the version comment is documentation, never the pin itself — do not
substitute a mutable branch or tag. Dependabot moves the SHA and its version
comment in this repository's own workflow when a release is cut, and the
pin-sync test forces this example to follow.

```yaml
name: pr gate
# pull_request_target: a fork's pull_request token is read-only, so its
# comment and close would silently do nothing. The pinned action reads the
# template at the PR's base SHA and runs no pull-request code.
on:
  pull_request_target:
    types: [opened, edited, reopened, ready_for_review]
permissions:
  contents: read
  issues: read
  pull-requests: write
concurrency:
  group: pr-gate-${{ github.event.pull_request.number }}
  cancel-in-progress: false
jobs:
  gate:
    # A reopen is authored by github-actions[bot] with this workflow's own
    # github.token, and GitHub's no-recursion exception holds such an event's
    # pull_request runs for approval: a draft closed and reopened loses its CI.
    if: >-
      github.event.pull_request.user.type != 'Bot'
      && github.event.pull_request.draft == false
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - uses: Nitjsefnie-Actions/pr-gate@b641821e74822ca7983d487f8c75865dcdebfaa8 # v1.0.0
        with:
          github-token: ${{ github.token }}
          repository: ${{ github.repository }}
          pull-request-number: ${{ github.event.pull_request.number }}
          pull-request-author: ${{ github.event.pull_request.user.login }}
```

No consumer checkout is needed. The action executes only its own code through
`github.action_path`. It reads the current PR, fetches the consumer template
through GitHub's contents API at that PR's **base commit SHA**, and asks GitHub
to render the body. It never checks out or executes PR-head code. Inputs enter
the process through environment variables, not shell-source interpolation.

The runner must provide Python 3.11–3.14 as `python`, Bash, and GitHub CLI `gh`.
GitHub-hosted runners provide these tools. Runtime Python code uses only the
standard library. For a self-hosted runner, install the tools before this step.

| Input | Meaning |
| --- | --- |
| `github-token` | Required token with the permissions in the example. |
| `repository` | Required consumer repository, `owner/name`. |
| `pull-request-number` | Required PR number. |
| `pull-request-author` | Required author login. |
| `template-path` | Optional consumer path; defaults to `.github/PULL_REQUEST_TEMPLATE.md`. |

## Admission rules

The template uses `##` section headings followed by instruction comments tagged
`Required`, `Conditional`, or `Optional`, without case sensitivity. Required
sections must appear. Included sections must have visible content, known names,
and template order. Duplicate/invented sections and retained template instruction
comments are rejected. The shipped [PR template](.github/PULL_REQUEST_TEMPLATE.md)
is an example consumer contract.

GitHub-rendered HTML is the sole authority for body section boundaries. Setext
headings, ordinary Markdown headings, and HTML headings follow their rendered
structure; heading-like text in code stays text. Footer, when present, must be
one final visible attribution line:

```text
Generated by GPT-6 Astra (implementation, testing), Another Model (review)
```

Bugs Discovered, when present, contains only rendered unordered-list items whose
visible text is `#N Literal issue title`. Every number must identify an existing
issue in the consumer repository, and the title must equal GitHub's title
exactly. Pull-request numbers, narrative entries, and mismatched titles fail.
Equivalent Markdown bullet markers are accepted. Escape Markdown metacharacters
when necessary to preserve an issue title's literal visible text.

At least one issue named in Related Issues and Pull Requests or by a body-wide
closing reference must be assigned to the PR author. Every closing issue must
be assigned to that author. Mere bug-list pointers do not substitute for this
assignment requirement. At most 20 distinct references are checked, sharing one
lookup cache between assignment and bug-title validation. Larger sets receive
a corrective comment.

The gate maintains one bot-owned marker comment. Layout/content failures can
close the PR, as can a claim failure with at least one checked issue reference;
more than twenty references, or no checked reference at all, leave the PR open
with a corrective comment unless a layout or content failure closes it first.
A corrective edit retries the same PR, and a gate-owned close reopens once all
conditions pass. When GitHub refuses that reopen — a force-push while the
pull request was closed is the usual cause — the gate says so in its comment,
with the two ways out: a maintainer reopen, or a fresh pull request from the
same branch. That reopen is authored by the bot with the workflow's own
`GITHUB_TOKEN`, so GitHub creates the CI runs it triggers without jobs and
held for approval; the author pushes once more afterwards — an empty commit
is enough — to get a verdict, and the reopen comment says so. The bot reopen
can also be counted by GitHub as an unattributed change, and a merge ruleset
that requires extra approval for unattributed changes can hold the merge
even with every check green; the reopen comment tells the author to close
and reopen the PR themselves once before merging when that happens.
Ownership survives interrupted reopen operations; maintainer closures and
changes in state/closer prevent unsafe writes. Assignment changes alone do
not trigger the workflow: edit or reopen the PR to request another check.

A successfully enforced decision exits zero, including a comment or close.
Analysis/API failures exit nonzero. This is an admission mechanic, not a red
status-check policy or a standalone issue-event workflow. Consumer repositories
remain responsible for assigning issues and their own merge policy.
